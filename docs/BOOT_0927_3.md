## 2. Bluetooth audio: `IBluetoothAudioProviderFactory/default` declared, no provider

### Facts

- 119 x `init: Could not find 'aidl/android.hardware.bluetooth.audio.IBluetoothAudioProviderFactory/default' for ctl.interface_start`
  from servicemanager, 44 x "Waited one second for ..." (evidence:61-63). `ctl.interface_start` is what
  servicemanager sends for a *declared* instance nobody has registered; init finds no service with that
  `interface aidl` line and reports the error.
- Who declares it: not `device/manifest.xml`, not `DEVICE_MANIFEST_FILE` (`device/BoardConfig.mk:111-120`),
  not a blob. It is the VINTF fragment of the AOSP module `android.hardware.bluetooth.audio-impl`
  (`hardware/interfaces/bluetooth/audio/aidl/default/Android.bp:11-13`, `vintf_fragments: ["bluetooth_audio.xml"]`;
  the fragment declares `android.hardware.bluetooth.audio` v5 `IBluetoothAudioProviderFactory/default`), which
  `device/device.mk` listed in `PRODUCT_PACKAGES` (line 83 before this PR, added on 26/09 with the WiFi/BT HAL
  blobs, commit ef09be2).
- Who provides it: nobody. The library only exports `createIBluetoothAudioProviderFactory()`; in AOSP the
  *audio HAL* calls it. Our audio HAL is Samsung's `secaudiohalaidl` (declares `vendor.samsung.hardware.audio`,
  `reference/stock/vendor/etc/vintf/manifest/secaudiohalaidl_manifest.xml:7-8`). The AOSP HCI service registers
  `IBluetoothHci` only (`hardware/interfaces/bluetooth/aidl/default/service.cpp:38-42`), and ours is the stock
  binary anyway (`proprietary-files.txt:1147`) whose fragment declares only `IBluetoothHci/default`
  (`reference/stock/vendor/etc/vintf/manifest/bluetooth-service-default.xml:7-8`).
- Stock never declares `android.hardware.bluetooth.audio`: no fragment in
  `reference/stock/vendor/etc/vintf/manifest/` names it; Samsung's Bluetooth audio HAL is
  `vendor.samsung.hardware.bluetooth.audio` v2 `ISehBluetoothAudioProviderFactory/default`
  (`seh_bluetooth_audio.xml:7-9`, in our image too, `proprietary-files.txt:636`), consumed by Samsung's own
  Bluetooth stack. Stock does ship the AOSP library file (`reference/stock/vendor_ls_Z.txt:2165`,
  `android.hardware.bluetooth.audio-impl.so`, 338592 bytes) without a fragment.
- Who waits: Lineage's Bluetooth stack probes the AIDL factory first
  (`packages/modules/Bluetooth/system/audio_hal_interface/hal_version_manager.cc:33-34, 140-143`;
  `GetAidlInterfaceVersion()` calls `AServiceManager_waitForService` on it, `:71-75`), and falls back to HIDL
  only when the AIDL instance is absent.

### Change

`android.hardware.bluetooth.audio-impl` removed from `PRODUCT_PACKAGES` (`device/device.mk`, comment in place);
`vendor/lib64/android.hardware.bluetooth.audio-impl.so` added to `device/proprietary-files.txt` so the file stays
in the image as the stock blob (a prebuilt carries no `vintf_fragments`), for whatever stock links it against.
The fragment `bluetooth_audio.xml` disappears with the module, so the lookup fails fast instead of blocking
(lesson of PR #11). Check 4 (`tools/check_manifest.py`) is unaffected: it only requires the stock instances.

What this does **not** give: a Bluetooth audio HAL for Lineage's stack. After this change the stack finds no
AIDL and no HIDL provider (`hal_version_manager.cc:146-175`) and A2DP/HFP audio is unavailable. Stock's provider
(`ISehBluetoothAudioProviderFactory`) is Samsung-specific and is not what the AOSP stack asks for. Providing the
AOSP one needs a vendor process that calls `createIBluetoothAudioProviderFactory()` *and* an audio HAL that
consumes the sessions (`libbluetooth_audio_session_aidl`), i.e. new code, out of scope here.

Verify on the next boot: `once.txt` "vintf fragments" must not list `bluetooth_audio.xml`; the 119 init errors
must be gone.

## 3. Wi-Fi MAC / BT address

### `macloader` did run

- `init.svc.macloader=stopped` (evidence:51) is the state init writes when the process has exited:
  `Service::Reap` -> `NotifyStateChange("stopped")` for a `disabled`/`oneshot` service
  (`system/core/init/service.cpp:263, 312-317`); `NotifyStateChange` is the only writer of `init.svc.<name>`
  (`:175-181`). A service that was never started has no `init.svc.` property at all.
- Trigger and definition are the stock ones: `on post-fs-data ... start macloader`
  (`device/rootdir/etc/init/wifi.rc:4,57` = stock `reference/stock/vendor/etc/init/wifi.rc:4,55`), service
  `class main`, `user wifi`, `disabled oneshot` (`:78-84` = stock `:76-82`). The scsc modules it needs are loaded
  at `early-init` by `insmod_sh_common` (`reference/stock/vendor/etc/init/init.s5e8855.rc:13-14`), so the order is
  the stock one. Its policy is stock's (`macloader` domain, stock CIL 14727-14749: `wifi_efs_file` rw
  14737-14738, `sysfs_wifi` write 14748; label `device/sepolicy/vendor/file_contexts:48` = stock
  `vendor_file_contexts:50`), and the evidence lists no `macloader` denial.
- Its input is `/mnt/vendor/efs/wifi/.mac.info` (`wifi.rc:46-52`), its output `/sys/wifi/mac_addr` (`:51`).
  Whether it succeeded is not in the evidence; the boot catcher now lists `/mnt/vendor/efs/wifi`, `/sys/wifi` and
  `/sys/class/net` in `once.txt`.

### `wlbt_dcxo_caldata`

- `Direct firmware load for wifi/wlbt_dcxo_caldata failed with error -2` (evidence:42) is the driver's
  `request_firmware()` looking for `/vendor/firmware/wifi/wlbt_dcxo_caldata` (ENOENT). **Stock has no such file
  either**: stock `/vendor/firmware/wifi` holds `hydra_config.sdb`, `mx140/`, `mx140*.bin/.hcf/.htf/.sdb`,
  `platform.txt`, `slsi_reg_database.bin` (`reference/stock/vendor_ls_Z.txt:1326-1343`), the same 14 entries as
  ours (`reference/ours/vendor_ls_Z.txt:1323-1339`). The kernel has no built-in copy (`CONFIG_EXTRA_FIRMWARE=""`,
  `reference/stock/kernel/ikconfig.txt:1797`) and no user-helper fallback (`:1799`).
- On stock the calibration data reaches the driver through the sysfs node `/sys/wifi/wlbt_dcxo_caldata`:
  `wifi.rc` chowns it to `wifi` (`device/rootdir/etc/init/wifi.rc:20-21` = stock `:18-19`, also `wifi_slsi.rc:47-48`),
  and the writers stock allows are `macloader` (`sysfs_wifi` rw, CIL 14748) and the Wi-Fi HAL (`hal_wifi_default`
  `sysfs_wifi` rw, CIL 8204). The warning is therefore expected on stock too and is not a regression; no change.

### `vendor.bluetooth_fw_ver` (15 denials, evidence:119)

Stock's `vendor_property_contexts` has no entry for it (its only bluetooth entries: `vendor.bluetooth_slimbus_fail`
:306 and `persist.vendor.qcom.bluetooth.soc` :313, both `vendor_bluetooth_prop`), so on stock it is
`vendor_default_prop` as well, and stock lets `hal_bluetooth_default` set only `wifi_log_prop` (CIL 7771),
`vendor_bluetooth_prop` (11932), `sec_bluetooth_prop` (11941) and `vendor_bdroid_service_prop` (11959): the same
denial occurs on stock. Fix in `device/sepolicy_extra/property_contexts`: `vendor.bluetooth_fw_ver ->
vendor_bluetooth_prop` (the type of stock's other `vendor.bluetooth_*` entry; `vendor.` is an allowed vendor
prefix, `build/soong/selinux_contexts.go:365-381`). Check 1 validates the file (types, duplicates, neverallows).

### BT address

`ro.bt.bdaddr_path=/mnt/vendor/efs/bluetooth/bt_addr` (evidence:58) is set by the stock script
`vendor.samsung.hardware.bluetooth-default.rc:11` (in our image, `proprietary-files.txt:520`), which also creates
and chowns the directory (`:3-8`); the path is `bluetooth_efs_file` (stock `vendor_file_contexts:1064` =
ours). No denial on it in the evidence, both Bluetooth services run (evidence:52-53). Why Settings shows no
address is not in the evidence; needed: the `bt_stack`/`bluetooth` logcat lines at enable time and the
`/mnt/vendor/efs/bluetooth` listing now in `once.txt`.

### No `wpa_supplicant` after Wi-Fi on

Its rc is in the image (`reference/ours/vendor_ls_Z.txt:613`, `proprietary-files.txt`
`android.hardware.wifi.supplicant-service.rc`), stock content: `disabled`, `interface aidl

(now in `once.txt`).
