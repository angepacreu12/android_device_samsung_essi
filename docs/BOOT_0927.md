# 27/09 boot: navigation bar / display, USB data, Wi-Fi module load, modem

/e/OS boots on the A56 (27/09): touch, sound, lock screen and volume work, SELinux enforcing, no
VaultKeeper/CASS/KG. Four things do not work. This note gives, for each, the facts in the repository
(file:line), what this PR changes, and exactly which stock file is still needed when the repository does
not hold the answer. Paths under `reference/stock/vendor/etc/init/` are written as `init/<file>`; "stock
CIL" is `reference/stock/vendor/etc/selinux/vendor_sepolicy.cil`; "ours ls" and "stock ls" are
`reference/ours/vendor_ls_Z.txt` and `reference/stock/vendor_ls_Z.txt`. Lineage 22.2 framework
sources were read from `LineageOS/android_frameworks_base` and `android_system_core`, branch
`lineage-22.2`, and are cited by their path in those repositories.

Ranked by impact on the project: USB first because without it there is no adb and every other item is
investigated through the boot-log catcher only; then the UI (unusable without a navigation bar); then
Wi-Fi; then the modem, whose HAL declarations turn out to be complete.

## 1. USB data never comes up

### What the repository shows

**Stock declares no USB gadget HAL.** The Samsung USB HAL declares only `IUsb/default`
(`reference/stock/vendor/etc/vintf/manifest/android.hardware.usb-service.exynos.xml:6-10`, version 2).
No file in stock's `vintf/`, `vendor_hwservice_contexts` or `vendor_service_contexts` mentions
`gadget`, nor does ours (`device/manifest.xml`, `reference/ours/vendor/etc/vintf/`). The domain the
HAL runs in, `hal_usb_impl`, does carry `hal_usb_gadget_server` (stock CIL 1371) and may set
`vendor.usb.*` (CIL 6006; `vendor_property_contexts:78-79`), but an attribute is not a registration:
nothing declares `android.hardware.usb.gadget.IUsbGadget/default`, so servicemanager cannot have it,
on stock or on ours. `usbd`'s message is therefore the expected result of `usbd.cpp:53`
(`AServiceManager_isDeclared`), not a fault of our image; `usbd` only matters on the gadget-HAL path
(and starts adbd when `persist.sys.usb.config` is exactly `adb`, `usbd.cpp:47-50`).

**Stock configures the gadget from init, driven by `sys.usb.config`.** `init/init.s5e8855.usb.rc`
(568 lines, in our image: ours ls 639, `device/proprietary-files.txt:496`) has one block per function
set: `none` (85-100), `adb` (102-119), `mtp,conn_gadget` (121-138), `mtp` (163-178), `mtp,adb` (180-),
… Each block rewrites the configfs symlinks, writes `UDC ${sys.usb.controller}` (117, 176) and echoes
`sys.usb.state` (100, 118, 177). `sys.usb.controller` is set to `13200000.dwc3` at
`init/init.s5e8855.rc:235`. This is the legacy AOSP protocol: `system_server` sets `sys.usb.config`
and waits for `sys.usb.state` to match.

**The two properties that stayed unset are a replug helper, not the source of the configuration.**
After every successful switch the block also stores `vendor.usb.sys.config = sys.usb.config` (119,
138, 178). `on property:vendor.usb.dwc3.ready=1` re-applies that stored value (14-15) and `=0` forces
`none` (11-12). `vendor.usb.dwc3.ready` can only be set by `hal_usb_impl` or `vendor_init` (CIL 6006,
6839); no rc sets it. So: the HAL announces the controller, init re-applies the last configuration.
On our boot `vendor.usb.sys.config` was never written, which means no block after `none` ever ran,
i.e. `sys.usb.config` was never set to anything but `none`.

**`sys.usb.configfs=2` is intentional.** `init.s5e8855.usb.rc:69` sets it to 2. AOSP's
`init.usb.rc` reacts only to `sys.usb.configfs=0` (`init.usb.rc:32`) and `init.usb.configfs.rc` only
to `=1` (`init.usb.configfs.rc:1, 17, 20`), so on this device only Samsung's rc drives the gadget. Same
on stock.

**What Lineage 22.2 does with that.** `UsbService.java:204-205` creates `UsbDeviceManager` only if
`/sys/class/android_usb` exists. Our kernel has it: `CONFIG_ANDROID_USB_CONFIGFS_UEVENT=y`
(`reference/stock/kernel/ikconfig.txt:5191`, the config embedded in `device/prebuilts/kernel`,
`6.6.50-android15-8-abA566BXXS6AYGE-4k`). `UsbDeviceManager.java:345` asks
`UsbGadgetHalInstance.getInstance` (`UsbGadgetHalInstance.java:34-46`: AIDL if
`ServiceManager.isDeclared("android.hardware.usb.gadget.IUsbGadget/default")`,
`UsbGadgetAidl.java:94-102`, else HIDL, else null) and picks `UsbHandlerLegacy` when it is null
(`UsbDeviceManager.java:363-376`). So our framework is on the legacy path, the one the stock rc
implements. On that path, at boot: `finishBoot` (1524-1536) → `setEnabledFunctions(NONE)` →
`trySetEnabledFunctions` (2169-2224): with adb disabled the functions become `mtp`
(`getChargingFunctions`, 1773-1781), then `setUsbConfig("none")`, `waitForState("none")`,
`setUsbConfig("mtp")`, `waitForState("mtp")` (`waitForState`: 2064-2076, 20 × 50 ms on
`sys.usb.state`). Expected state at boot_completed: `sys.usb.config=mtp`, `sys.usb.state=mtp`,
`UDC=13200000.dwc3`, `vendor.usb.sys.config=mtp`. Observed: `none`, `none`, unset.

### Where it can break, and the log line that tells

| step | signature in logcat (`UsbDeviceManager`) or dmesg | source |
|---|---|---|
| `UsbDeviceManager` never constructed | no `UsbDeviceManager` lines at all; `once.txt` shows `android_usb=` empty | `UsbService.java:204` |
| gadget HAL probing | `USB Gadget HAL AIDL/HIDL not present` (must be there: confirms legacy) | `UsbGadgetHalInstance.java:44` |
| legacy handler init | `Error initializing UsbHandler` (STATE_PATH `/sys/class/android_usb/android0/state` unreadable) | `UsbDeviceManager.java:1976-1979` |
| kick to `none` | `waitForState(none) FAILED`, `Failed to kick USB config` (init did not run block 85-100) | 2074, 2202 |
| switch to `mtp` | `waitForState(mtp) FAILED`, `Failed to switch USB config to mtp`; in dmesg `init: Command 'write /config/usb_gadget/g1/UDC 13200000.dwc3' action=(sys.usb.config=mtp) ... returned ...` | 2221; `init.s5e8855.usb.rc:176` |

### Fix

Nothing in the tree is missing for the path the stock rc implements: HAL binary (ours ls 320), its
rc and fragment (611, 1068), `init.s5e8855.usb.rc` (639), `sys.usb.controller`
(`init.s5e8855.rc:235`), kernel uevent support (ikconfig 5191). Declaring `IUsbGadget/default` in
`device/manifest.xml` would not help: no process registers it, and servicemanager would then only
report the missing registration. The fix follows from the first row of the table above that matches
the next boot's `usb.txt`/`once.txt`/logcat. This PR extends the boot-log catcher accordingly
(`device/bootlog/essi_bootlog.sh`: `android_usb` state on every sample, `dumpsys usb`, `adb_enabled`
and the other captures once after boot). If the table shows the `mtp` block failing on the `UDC`
write, the follow-up is on the dwc3/type-C side (`CONFIG_USB_DWC3_DUAL_ROLE=y`, ikconfig 5034; role
handled by the `usb_typec_manager`/`usb_notifier` modules of `vendor_boot/modules.load:194-204` and
the IUsb HAL), not in the framework.

- `TARGET_SCREEN_DENSITY := 450` (`device/BoardConfig.mk:38`) is the only display geometry setting in

### This PR

`device/overlay/frameworks/base/core/res/res/values/config.xml` + `DEVICE_PACKAGE_OVERLAYS` in
`device/device.mk`: `config_showNavigationBar=true`; doze/AOD off
(`config_dozeAlwaysOnDisplayAvailable=false`, `config_dozeAfterScreenOffByDefault=false`, empty
`config_dozeComponent`, all AOSP defaults stated explicitly so the stock vendor RRO, if it is enabled,
cannot turn them on).

## 3. Wi-Fi: `insmod_sh_wifi` exits 1

### Facts

- Service: `init/init.exynos.wifi.rc:4` — `insmod_sh_wifi /vendor/bin/init.insmod.sh
  /vendor/etc/wifi/init.insmod.wifi.cfg`, started by `on property:vendor.system_dlkm.modules.ready=true`
  (:1-2). Bluetooth: `init/init.s5e8855.rc:654` with `/vendor/etc/init.insmod.bluetooth.cfg`, started
  at :15 together with `insmod_sh_system` (:13, :619) and `insmod_sh_common` (:14, :612, argument
  `vendor_dlkm`).
- The script is ours (`device/rootdir/bin/init.insmod.sh`, `device/device.mk:51`,
  `device/rootdir/Android.bp:20-21`), same size as stock's (3 050 bytes, stock ls 147 = ours ls 147).
  Grammar `action|arg` per line (:4-7). The cfg branch (:88-105) runs `insmod`, `setprop`, `enable`,
  `modprobe` or `insmod_16k` (:93-102) per line and prints nothing; the script's exit status is that
  of the last action, so **exit 1 = the last line of `init.insmod.wifi.cfg` failed**. The `vendor_dlkm`
  branch (:55-86) is `modprobe -s -b -d … --all=modules.load` with an insmod fallback.
- The cfg files are stock blobs not in the repository: `init.insmod.wifi.cfg` 79 bytes (stock ls
  1140, ours ls 1137, `proprietary-files.txt:348`), `init.insmod.bluetooth.cfg` 46 bytes (stock ls
  417, ours 417, `:679`), `init.insmod.vendor_dlkm.cfg` 0 bytes (stock ls 418, `:680`). Inference,
  to be confirmed from `once.txt` (it prints both cfgs): the only 46-byte line in the script's grammar
  that names a scsc Bluetooth module is `insmod_16k|/vendor/lib/modules/scsc_bt_16k.ko`, a no-op on
  our 4K kernel (`CONFIG_LOCALVERSION="-4k"`, ikconfig 33; `insmod_16k` runs only when PAGE_SIZE is
  16384, :97-102), which is why `insmod_sh_bluetooth` exits 0.
- Modules we ship: `device/prebuilts/modules/vendor_dlkm/modules.load` (55 entries, 56 `.ko`,
  `device/BoardConfig.mk:122-133`) lists `scsc_platform_mif.ko` (12), `scsc_mx.ko` (13),
  `scsc_mmap.ko` (15), `scsc_bt.ko` (16), `scsc_wlan.ko` (17), `scsc_wifilogger.ko` (18). They are
  loaded by `insmod_sh_common` (modprobe of the whole list) **before** the wifi cfg runs. If that cfg
  `insmod`s any of them, `insmod` fails with "File exists" and the service exits 1 while the module
  is in fact loaded. `/vendor/lib/modules` is a symlink to `/vendor_dlkm/lib/modules` on both images
  (stock ls 2142, ours ls 2139).
- `scsc_bt_16k.ko` is the one `.ko` in `vendor_dlkm/` absent from `modules.load` (comm of the two
  lists). That is correct for a 4K kernel: it is meant to be loaded by the `insmod_16k` action only.
  The preflight warning is expected; nothing to change.

### Fix

Depends on the cfg content, captured by `once.txt` together with `lsmod`:
- cfg `insmod`s modules already in our `modules.load` → exit 1 is cosmetic if `lsmod` shows
  `scsc_wlan`; the stock-faithful change is to make `vendor_dlkm/modules.load` match stock's, which
  needs **stock `/vendor_dlkm/lib/modules/modules.load` and `modules.dep`** (the vendor_dlkm partition
  is not in `reference/stock/`).
- cfg names a module we do not ship (nothing `scsc_*` beyond the six above is in `vendor_dlkm/`) →
  add it to `device/prebuilts/modules/vendor_dlkm/` and `modules.load`.
Files needed: `/vendor/etc/wifi/init.insmod.wifi.cfg` (79 bytes) and stock's vendor_dlkm
`modules.load`.

### What the RIL init scripts expect and do not get

- `init/init.vendor.rilcommon.rc:35` (in our image: ours ls 642, `proprietary-files.txt:500`):
  `setprop ro.telephony.default_network ${ro.vendor.radio.default_network}`.
- `init/init.baseband.rc:28-35` (ours ls 629, `:487`): `ro.vendor.multisim.simslotcount` drives
  `write /sys/module/cpif/parameters/ds_detect` (28-29) and `persist.radio.multisim.config` = `ss`
  or `dsds` (31-35).
- Neither `ro.vendor.radio.default_network` nor `ro.vendor.multisim.simslotcount` is set anywhere in
  the tree (`grep` over `device/*.prop`, `device/*.mk`). The radio properties we do set are
  `ro.radio.noril=no`, `ro.telephony.default_cdma_sub=0` (`device/vendor.prop:41-42`) and
  `ro.vendor.sec.radio.def_network=9` (`:130`, a different name). Consequences on our boot:
  `ro.telephony.default_network` is set to an empty string, `ds_detect` is never written,
  `persist.radio.multisim.config` stays unset (single-SIM framework).
- `ril-daemon` (`init/vendor.samsung.rild.rc:6-14`, `class main`, user `radio`) and `cpboot-daemon`
  (`init/init.baseband.rc:20-23`) are the processes seen running; `ril.RildInit=1,1` is the RIL's own
  report.

### Fix

Set the two properties with stock's values. They live in stock's **`/vendor/build.prop`**, which is
not in `reference/stock/` (the tree's `device/vendor.prop` is curated, not a copy). Needed:
`/vendor/build.prop` (for `ro.vendor.multisim.simslotcount`, `ro.vendor.radio.default_network` and the
other `ro.vendor.radio.*`/`persist.vendor.radio.*` entries) and `/system/build.prop`
(`persist.radio.*`, `ro.telephony.*`). Not set here, to avoid guessing a slot count. `once.txt` records
`service list | grep hardware.radio` (whether the RIL registered the AOSP instances) and every
radio/telephony property.
