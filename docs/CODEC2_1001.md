# Codec2 01/10: `samsung.hardware.media.c2@V1-service` crashes on its first codec

## Facts (quoted)
- `docs/logs/diag_1001_1203/01_crash_log.txt:9-34` (30/09, 16:33:43): `media.hwcodecw/samsung.hardware.media.c2@V1-service`,
  `signal 11 (SIGSEGV), code 1 (SEGV_MAPERR)`. Backtrace:
  ```
  #00 /vendor/lib64/libcodec2_aidl.so (ComponentStore::reportComponentBirth(Component*)+104)
  #01 /vendor/lib64/libcodec2_aidl.so (ComponentStore::createComponent(...)+932)
  #02 /vendor/lib64/android.hardware.media.c2-V1-ndk.so (IComponentStore_onTransact+2064)
  #06 /vendor/bin/hw/samsung.hardware.media.c2@V1-service (runService()+508)
  ```
  So the service starts and registers, and dies on the first `createComponent` call from a client.
- 01/10 14:49 (user's crash grep, posted in the Bluetooth thread): 4 more crashes of the same service, pids 771, 2684,
  2902, 3020, about 5 s apart. Only the header lines were posted; the frames were not. Assumed to be the same crash
  until a full `adb logcat -b crash -d` of a build without the patch says otherwise.
- The service binary is Samsung's blob (`device/proprietary-files.txt:371`); its rc is unchanged from stock
  (`reference/ours/vendor/etc/init/samsung.hardware.media.c2@V1-service.rc` = `reference/stock/...`, `diff` empty).
- `libcodec2_aidl.so` is **not** the stock one. We build AOSP's (`device/device.mk:196`, `libcodec2_aidl.vendor`;
  dep stripped by `device/fix-bp.sh:3`). Sizes: stock 257024 bytes (`reference/stock/vendor_ls_Z.txt:2313`), ours
  290224 (`reference/ours/vendor_ls_Z.txt:2313`).
- Stock vendor was built from `AP3A.240905.015` (`reference/stock/extra/vendor/build.prop`,
  `ro.vendor.build.fingerprint=samsung/a56xnaxx/a56x:15/AP3A.240905.015.A2/A566BXXS6AYGE`).

## Cause
`LineageOS/android_frameworks_av` lineage-22.2, `media/codec2/hal/aidl/include/codec2/aidl/ComponentStore.h`:
- line 131 `std::shared_ptr<C2ReflectorHelper> mMultiAccessUnitReflector;` (16 bytes), between `mParamReflectors` (128)
  and the rest;
- line 146 `std::map<Component*, ComponentStatus> mComponentRoster;`, the last data member;
- `ComponentStore.cpp:441-447`: `reportComponentBirth()` locks `mComponentRosterMutex` and does
  `mComponentRoster.emplace(...)`. That is frame #00.

The member was added by upstream commit `07b6b1570b` "MultiAccessUnit reflector helper allocated once per
ComponentStore" (Arun Johnson, committed 2024-09-10, bug 365014948), to the AIDL and the three HIDL `ComponentStore`
classes. It is the only change to those class layouts in lineage-22.2 since mid-2024 (`git log` on the include dirs:
`4efd3ed021` adds new files only, `4aa99a8438` adds a comment).

The service allocates the store itself (AOSP's pattern, `media/codec2/hal/aidl/fuzzer.cpp:30`:
`SharedRefBase::make<ComponentStore>(store)`, a template inlined in the caller), so the allocation size is the one from
the headers Samsung compiled against. **Inferred, not proven from the blob:** Samsung's build (`AP3A.240905`, branch cut
before 2024-09-10) does not have the member, so the object it allocates is 16 bytes short. Our library's constructor
then initialises `mComponentRoster` partly outside the allocation, the heap reuses those bytes, and the first `emplace`
on the corrupted map faults with `SEGV_MAPERR`, which is what the backtrace shows. The blob was not disassembled
(no blob in the repo) to confirm the size it passes to `operator new`.

## Fix
`patches/frameworks/av/0001-codec2-keep-ComponentStore-layout-of-prebuilt-vendor.patch`, against lineage-22.2
`0bbac29e2a`. It removes the member from the four headers and keeps the upstream behaviour: the reflector is still
created once in the constructor and pushed last into `mParamReflectors` (nothing pushes after the constructor), and
`tryCreateMultiAccessUnitInterface()` takes `mParamReflectors.back()`. A plain revert of `07b6b1570b` would also restore
the layout, but it brings back the per-component `mParamReflectors.push_back()` from binder threads that the upstream
commit removed.

Why not the stock `libcodec2_aidl.so` blob instead: it would match the service, but it was built against Samsung's own
`libcodec2_vndk` / `libcodec2_hal_common` / bufferpool2, and we ship AOSP builds of those (`device/device.mk:196-197,
235-239`), which `frameworks/av` changed after September 2024 (e.g. `media/codec2/hal/common`: `7fed726f2d`
2024-10-15, `587aa32bcb` 2024-11-19). Not checked symbol by symbol; the patch keeps every codec2 library from one
source tree instead.

The HIDL `samsung.software.media.c2@1.0-service` is not seen crashing, but it uses the same `ComponentStore` layout
through our `libcodec2_hidl@1.0`, so the patch covers the HIDL headers too.

## Check after the build
- `git -C frameworks/av apply --check` on the patch before building (`patches/README.md`).
- After flashing: `adb logcat -b crash -d | grep -c hwcodecw` should print 0 after playing a video (hardware decoder),
  and `adb shell ps -A | grep hwcodecw` should show the same pid before and after playback.
