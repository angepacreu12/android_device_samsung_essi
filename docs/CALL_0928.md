## 1. Voice call

### 1a. What the Samsung RIL expects from the framework for an MO CS call on LTE

- **The RIL binary is not in the reference.** No `.so` is kept, so its internal logic cannot be read. What the
  references do show is the interfaces it serves and the Samsung-specific callbacks it sends.
- **Standard voice interface: served and bound.** The RIL declares `android.hardware.radio.voice` v3
  `IRadioVoice/slot1,slot2`
  (`reference/ours/vendor/etc/vintf/manifest/vendor.samsung.hardware.radio_manifest_2_202404.xml:57-62`,
  byte-identical to stock). Lineage's RIL binds it and registers `mVoiceResponse` / `mVoiceIndication`
  (L-ot `RIL.java:1029-1033`). The live log confirms it: `DIAL` and `GET_CURRENT_CALLS` go through.
- **Samsung-only call callbacks.** The Samsung network interface has `callDetailsChanged` and `csFallback`
  indications (L-hws `interfaces/radio/network/aidl/.../ISehRadioNetworkIndication.aidl`; Lineage's client stubs
  them at `ril/sehradiomanager/aidl/SehRadioNetworkIndication.cpp:35-44`). The RIL reports CS fallback progress to
  **Samsung's** client, which nothing on our image registers. The RIL logs `mSeh…Indication == NULL` when it has
  nothing to send to (task: `stkCallControlResultInd: mSehRadioSimIndication == NULL`).
- **"Framework ready".** Lineage's published client for this RIL generation, `sehradiomanager`, does two things
  per slot (L-hws `ril/sehradiomanager/sehradiomanager.cpp:94-107`):
  - It registers response and indication callbacks on `ISehRadioNetwork/slotN`.
  - It sends `setVendorSpecificConfiguration(0x4242, config)`. The config defaults to `FW_READY=1` when
    `/vendor/etc/sehradiomanager.conf` is absent (:88-92).
  - It starts on `sys.boot_completed=1` (`ril/sehradiomanager/sehradiomanager.rc:1-8`).
  - Lineage introduced it for "signal bar, LTE+ and 5G … with RIL stacks from stock Android S and up" (commit
    d6f5799, 2024-03-11). It is based on TrebleDroid's telephony change "Initialize Samsung HIDL ISehRadio. Fixes 5G
    on S20 Ultra" (f0eecb08). No source ties it to calls.
  - Our earlier capture shows `ril.phone.connected.slot1=false` and `ril.phone.connected.slot2=false`
    (`docs/BOOT_0927_3_evidence.txt`, radio block). That suggests the RIL tracks some framework-connected state.
    What sets it to true cannot be read without the binary.
- **STK call control and "fake call".** Lineage's client registers `ISehRadioNetwork` only, not `ISehRadioSim`
  (`sehradiomanager.cpp:97-107`). Lineage Samsung devices therefore also run with `mSehRadioSimIndication == NULL`.
  That is weak evidence that the STK call-control result is not what blocks. Nothing in the references says the RIL
  waits on it. "DetermineKeepFakeCall … not initialized" is logged at dial and at hang-up alike, so it does not
  mark the stall.
- **Voice domain props: same as stock.**
  - `ro.vendor.sec.radio.def_network=9`, i.e. `NETWORK_MODE_LTE_GSM_WCDMA` (L-fb
    `telephony/java/com/android/internal/telephony/RILConstants.java:181`), on stock
    (`reference/stock/extra/vendor/build.prop:86`) and ours (`device/vendor.prop:130`).
  - Live `persist.radio.def_network=26`, i.e. `NETWORK_MODE_NR_LTE_GSM_WCDMA` (`RILConstants.java:232`). 2G and 3G are
    allowed, so a CSFB target exists.
  - `ril.lte.voice.status=1` (`docs/BOOT_0927_3_evidence.txt`).
  - The stock vendor `build.prop` has no other voice or IMS prop, and neither does ours.
  - Samsung's per-carrier voice-domain switches live in the EUX OMC files, `cscfeature.xml` and
    `customer_carrier_feature.json` (`docs/CSC_phone_0927.txt:92-99`). Their contents are not in the repo, and
    Samsung's framework consumes them, not the RIL.
- **Framework VoLTE switches.** Ours are off by default: `config_device_volte_available` and
  `config_carrier_volte_available` are false (L-fb `core/res/res/values/config.xml:3804`, :3809). Stock framework-res
  has both true (FR :390509, :389860), but stock has an ImsService. With no ImsService, AOSP dials CS, which is what
  `DoDial … CallDomain 0` shows.

### 1b. Is the standard voice indication registered?

- **Yes.** `RIL.java:1029-1033` registers `mVoiceIndication` on `IRadioVoice`, and the live log shows `DIAL`
  going through it.
  - *Corrected 28/09 (`docs/VERIFY_0928.md`):* an earlier version said voice services are bound only when
    `FEATURE_TELEPHONY_CALLING` is present (`RIL.java:296`). That is wrong. The map at `RIL.java:295-296` is read
    only by `validateFeatureFlags()` (`RIL.java:1307-1324`), which logs a feature/service mismatch and gates
    nothing.
- In the call window the task quotes only one NULL indication, and it is Samsung's SIM one.
- So the absence of `UNSOL_RESPONSE_CALL_STATE_CHANGED` means the RIL sent no call-state change. Either the modem
  never progressed the call or the RIL held it. It is not a missing framework callback.
- To confirm on the full log, grep for `Indication == NULL` over the whole radio buffer (1e).

`reference/ours/vendor/etc/vintf/manifest/vendor.samsung.hardware.sehradio_manifest_2_202404.xml` (identical to

| HAL | instances | line | client on stock | client on ours | Lineage precedent |

| `vendor.samsung.hardware.radio.bridge` `ISehRadioBridge` | slot1, slot2 | 6-10 | Samsung framework | none | none |
| `…radio.channel` `ISehRadioChannel` | epdgd, epdgd2, imsd, imsd2 | 11-17 | Samsung ePDG/IMS | none (no IMS) | none |
| `…radio.data` `ISehRadioData` | slot1, slot2 | 18-22 | Samsung framework | none | none |

- Lineage publishes the interface for the network one only: `interfaces/radio/network/aidl`, version 1, hash

  Lineage found worth a client.

### 1d. Proposed fix, not applied in this PR

**Ship Lineage's `sehradiomanager`.** It is a client, not a service, so it declares nothing. Three prerequisites
must hold first, and each can break the build or the RIL if wrong:

1. **`hardware/samsung` must be in the build.** It is not referenced anywhere in this repo, and there is no
   `lineage.dependencies`. Adding `LineageOS/android_hardware_samsung` (`lineage-22.2`) to the /e/OS local
   manifest is Ange's call. Without it, `PRODUCT_PACKAGES += sehradiomanager` fails the build.
2. **Library name clash.** Our tree ships stock's `vendor/lib64/vendor.samsung.hardware.radio.network-V1-ndk.so`
   (`device/proprietary-files.txt:204`). Lineage's `aidl_interface` builds a library with the same name, and both
   would install to the same path.
   - Before choosing which one wins, check that the interface hashes match (1e item 6).
   - If they match, drop the blob line and let the Lineage-built library serve both rild and `sehradiomanager`.
   - If they differ, the Lineage client cannot talk to this RIL as is.
3. **SELinux policy.** `hardware/samsung` ships none for it. It needs a `vendor` domain for
   `/vendor/bin/hw/sehradiomanager` with binder access to `ISehRadioNetwork`, in `device/sepolicy_extra/`.
   The stock type for that service is in the generated `device/sepolicy/vendor/service_contexts`.

Whether this makes calls progress cannot be proven from the references. The Lineage commit only claims signal and
5G fixes. It is the one published, low-risk step that makes our side behave like a Lineage Samsung device. If the
1e captures show the RIL waiting on `FW_READY` or showing `phone.connected=false` at dial time, it becomes the fix.
Otherwise the problem is on the modem or network side:
- CSFB not triggered;
- SMS accepted by the network but not delivered, which points at the CS/SGs side for both calls and SMS;
- the earlier silent modem reset (`persist.radio.silent-reset=1`).

## 2. Settings crash on the SIM page

### How the crash happens

1. `ImsQueryEnhanced4gLteModeUserSetting.query()` calls `ImsMmTelManager.isAdvancedCallingSettingEnabled()`
   (L-set `src/com/android/settings/network/ims/ImsQueryEnhanced4gLteModeUserSetting.java:43-47`).
2. The phone process refuses it without `FEATURE_TELEPHONY_IMS`
   (L-tel `src/com/android/phone/PhoneInterfaceManager.java:4970-4975`, check at :14761-14781). The check applies
   only when `ro.vendor.api_level` is 35 or later (:14770; value read at :2509-2510).
3. Ours is `202404` (`device/vendor.prop:111`, stock `reference/stock/extra/vendor/build.prop:40`). That is why this
   crash hits us and not older Lineage devices.

### Why hiding the preference cannot stop it

- **The preference is already unavailable.** `getAvailabilityStatus()` returns `CONDITIONALLY_UNAVAILABLE` unless
  VoLTE is provisioned and ready (L-set `.../telephony/Enhanced4gBasePreferenceController.java:98-120`). Our
  `config_device_volte_available` is false (L-fb `config.xml:3804`), and that is why the switch is not shown.
  - `KEY_HIDE_ENHANCED_4G_LTE_BOOL` (:110-112) would give the same result: unavailable.
- **But the crash does not go through availability:**
  - An unavailable preference is only made invisible, and it stays in the screen (L-fb
    `packages/SettingsLib/.../AbstractPreferenceController.java:67-68`).
  - The controller still stores it (`Enhanced4gBasePreferenceController.java:125`) and still registers its
    call-state callback in `onStart` (:133). `init()` always creates that callback (:72-75, called from
    `MobileNetworkSettings.java:322`).
  - The callback runs `updateState(mPreference)` (:220-222). Then `TogglePreferenceController.updateState` calls
    `isChecked()` (L-set `core/TogglePreferenceController.java:68-70`), and `isChecked()` calls
    `VolteQueryImsState.isEnabledByUser()` (:178-180), which makes the IMS call above.
  - This matches the task's stack trace line for line.
- **The only device-side ways out are both ruled out.** One is declaring IMS, which is forbidden. The other is
  lowering `ro.vendor.api_level`, which is a stock value that other compatibility checks rely on.

**Fix.** Apply `patches/packages/apps/Settings/0001-Settings-VolteQueryImsState-don-t-query-IMS-without-FEATURE_TELEPHONY_IMS.patch`.
- `VolteQueryImsState.isEnabledByUser()` returns false when the device lacks `FEATURE_TELEPHONY_IMS`. That is
  the guard the same class already uses in `isVoImsOptInEnabled()` (L-set `.../ims/VolteQueryImsState.java:146-151`).
- It is checked with `git am` against the pristine lineage-22.2 file. It fixes every caller of
  `isEnabledByUser()`, not only this preference. How to apply it is in `patches/README.md`.
- Remove it once IMS exists.

## 3. `sec-camera-provider` crash loop (note only)

- **What init reports.** "exited 4 times in 4 minutes" is init's branch for a process "with updatable components"
  (L-core `init/service.cpp:364-372`, :391-395). Besides logging, it sets
  `sys.init.updatable_crashing=1` "to notify update_verifier and apexd". So the loop is not only a battery cost.
- **A plain stop does not hold.** The provider is declared in VINTF, as
  `android.hardware.camera.provider.ICameraProvider/internal/0`
  (`reference/ours/vendor/etc/vintf/manifest/vendor.samsung.hardware.camera.provider-service.xml:6-10`). When any
  client, such as cameraserver, looks up a declared instance that is not registered, servicemanager sets
  `ctl.interface_start` (L-native `cmds/servicemanager/ServiceManager.cpp:872-884`). init then starts the service
  again, even a `disabled` one, because its rc names the interface
  (`reference/ours/vendor/etc/init/vendor.samsung.hardware.camera.provider-service_64.rc:1-2`). So a `stop` or `disabled` would be undone within
  seconds.
- **What would hold.** Leaving out both its rc and its VINTF fragment until the camera task. Nothing else depends on
  it: cameraserver would see no provider, and camera and torch are already broken. That is the only
  "stop the loop" that holds, and it is safe apart from losing camera diagnostics.
- **Not done here.** The next task needs the crash itself, with exit status 237, to debug the camera.
- **`proca`.** It is already in our image, unchanged from stock (`reference/ours/vendor/etc/init/pa_daemon_teegris.rc`,
  identical to stock). It starts on `vendor.tzdaemon=Ready` (:8-12). This PR does not touch it.
