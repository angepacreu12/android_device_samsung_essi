## 1. VoLTE shown as available, and what the switch reads

### Why calls already work although VoLTE is "off"

- The live carrier config says VoLTE is not available: `carrier_volte_available_bool = false`
  (`docs/response_0928.md:16`).
- Calls still go over IMS: the 01/10 call ended with `510 CODE_USER_TERMINATED_BY_REMOTE`
  (`04_telephony_registry.txt:21`), and SMS go over IMS (`05_ril_ims_logcat.txt:2475`, `:2506`).
- The reason is PhhIms: after each SIP registration it reports **voice and SMS as capable**, whatever the framework
  asked for (W22 `app/src/main/java/me/phh/ims/PhhMmTelFeature.kt:212-220`, called at `:709`
  `refreshMmTelCapabilities("SIP registered")`). The framework's own "enable/disable" requests are only logged and
  stored (`:142-171`).
- So the switch is a UI question here, not what makes calls work.

### What the Settings switch reads

The "VoLTE / 4G calling" switch on the SIM page is `Enhanced4gBasePreferenceController`:
- It is shown only if `VolteQueryImsState.isReadyToVoLte()` is true (Settings
  `src/com/android/settings/network/telephony/Enhanced4gBasePreferenceController.java:115-117`), or if VoIMS opt-in
  is provisioned (`:105-107`), and if `hide_enhanced_4g_lte_bool` is false (`:110-113`).
- `isReadyToVoLte()` = `isVoLteProvisioned()` and the MmTel feature is READY (Settings
  `src/com/android/settings/network/ims/VolteQueryImsState.java:94-107`).
- `isVoLteProvisioned()` = provisioned on device and `isEnabledByPlatform()` (`:74-87`), which is
  `ImsMmTelManager.isSupported(VOICE, WWAN)` (`ImsQueryController.java:66-82`).
- The phone process forwards that to `ImsManager.isSupported()` (Telephony
  `src/com/android/phone/PhoneInterfaceManager.java:4933-4963`), which for voice on WWAN returns
  `isVolteEnabledByPlatform()` (ims14 `src/java/com/android/ims/ImsManager.java:747-755`):
  - `persist.dbg.volte_avail_ovr` = 1, **or**
  - VoIMS opt-in provisioned, **or**
  - `config_device_volte_available` **and** `carrier_volte_available_bool` **and** a GBA check that passes when
    `carrier_ims_gba_required_bool` is false (`:801-821`, `:1595-1614`; Free has it false,
    `docs/response_0928.md:13`).
- The switch is editable when `editable_enhanced_4g_lte_bool` is true and no call is active (`:207-212`; AOSP default
  true, fw/base `telephony/java/android/telephony/CarrierConfigManager.java:10959`).

The **"VoLTE provisioned"** switch in `*#*#4636#*#*` reads the same `isSupported(VOICE, WWAN)` (Telephony
`src/com/android/phone/settings/RadioInfo.java:2634-2637`). It is checked when that is true and editable only on a
non-`user` build when the carrier requires provisioning (`:2320-2328`). Free does not
(`carrier_volte_provisioning_required_bool = false`, `docs/response_0928.md:19`), and our build is `user`
(`01_crash_log.txt:4`), so it will show **checked and greyed out**. That is expected.

### The two values, and where they come from

  `AndroidManifest.xml`, `vendor: true`). The PhhIms fork says the same: framework overlay plus CarrierConfig overlay
  (W22 `README.md:297`; README `353a65b` :366-381).
- **Not used:** `persist.dbg.volte_avail_ovr`. The fork calls it a bring-up helper, not a replacement for carrier
  config (README `353a65b` :307-318).

### Changes

- `device/overlay/frameworks/base/core/res/res/values/config.xml`: `config_device_volte_available=true`.
  Without `android.hardware.telephony.ims` the value is never read (`PhoneInterfaceManager.java:4936-4939` throws

**Side effect to know.** With VoLTE "available", turning the switch **off** makes the framework ask PhhIms to drop
voice. PhhIms' next registration re-reports voice anyway (`PhhMmTelFeature.kt:709`), so the effect is unclear. Keep
the switch on: off has no use on Free, where CS fallback lands on Orange and fails (`docs/IMS_0928.md`, "No-IMS
interim").

## 3. RCS

- `ImsProvisioningController: Rcs ImsService is not available, EAB provisioning status should be read from MmTel
  ImsService` appears 16 times (first at `05_ril_ims_logcat.txt:2151`). It is a debug line: the framework falls back to
  MmTel for that status.
- **PhhIms implements MMTEL only.** Its manifest declares `MMTEL_FEATURE` and `EMERGENCY_MMTEL_FEATURE`, no
  `RCS_FEATURE` (W22 `app/src/main/AndroidManifest.xml:31-32`), and `createRcsFeatureForSubscription` returns `null`
  (`app/src/main/java/me/phh/ims/PhhImsService.kt:101-106`). Its README lists RCS as "not a goal for now" (:47).
- **No open-source RCS client for AOSP 15 was found.**
  - The only open RCS stack found is `android-rcs/rcsjta` (Apache-2.0, README :18-19). It is a standalone RCS-e
    "Blackbird" app with its own SIP stack and a GSMA API (README :6), not an Android `ImsService` `RcsFeature`, and
    its last commit is `0844098` on 2017-03-08.
  - PhhIms and its forks (`phhusson/ims`, `krazey/ims`) are one codebase, MMTEL only (`docs/IMS_0928.md` §1).
- **Nothing to add (asked again on 01/10).** RCS through Android needs an `ImsService` that returns an `RcsFeature`
  (single registration). No open-source one exists, and writing one inside PhhIms is a new SIP/MSRP client, not a
  device-tree change. Google Messages' RCS and Samsung's are proprietary and excluded by the task rules. Nothing in
  this PR blocks a later client: the framework already looks for one, which is the line above.

  the A546B). Free registers and carries calls with the current one, so nothing is blocked.

## 5. Audio: downlink underruns

**What the log line means.** PhhIms plays the downlink in a 20 ms loop (W22
`app/src/main/java/me/phh/sip/SipDownlinkPcmPlayout.kt:51-96`). When the decoded queue is empty at a tick, it repeats
an attenuated copy of the last frame, for at most 6 frames (`:12`, `:63-71`), then plays silence. It logs
`concealed underrun` at the 1st and the 6th missing frame (`:76-82`). The queue holds 8 frames
(`SipDownlinkPcmPlayoutBuffers.kt:16`), and the loop starts writing 60 ms after the call audio starts (`:48`).

**What 01/10 shows** (the 09:22 call, `05_ril_ims_logcat.txt:162-1796`, about 47 s captured):
- 96 underruns. Recovery lengths: 36 after 1 frame, 10 after 2, 5 after 3, 5 after 5, then **40 gaps of 6-9 frames,
  i.e. 120-180 ms** (`recovered after fillerFrames=` counts).
- A 120 ms hole, about once a second, is very likely audible as choppy audio. The tester's own report decides it (question
  below).

**Known upstream, and fixed there.** Two commits on `lineage-23.2` change exactly this file:
- `8d91919` (2026-07-03, krazey), "ims: avoid startup downlink concealment repeats": no last-frame repetition until 4
  real frames have played.
- `8903a97` (2026-07-03, krazey), "ims: rebuffer downlink PCM after underruns": waits for a small queue (3 frames) at
  start, and after 12 missing frames rebuilds a 2-frame queue before resuming. Its message describes the symptom:
  "the decoded PCM queue may repeatedly drain to zero once speech arrives, causing local audio to sound jittery".
- Both predate the Samsung-derived carrier database (`1e216c7`, 2026-07-16), touch only `SipDownlinkPcmPlayout.kt`,
  and cherry-pick cleanly onto `4562d77`. The result equals the upstream file at `8903a97` (blob `d7db36a`).

**No buffer setting exists.** All these sizes are `const val` in the code; there is no property. The only audio
properties PhhIms reads are uplink gain (`SipUplinkGain.kt:5`) and network selection (`ImsNetworkRequestBuilder.kt:10`,
`ImsNetworkState.kt:153`).

**Change:** `patches/packages/apps/PhhIms/0001-…`, `0002-…` (`git format-patch` of the two commits on top of
`4562d77`). The build must apply them after cloning `projects.txt` (`patches/README.md`). A later fix,
`081a036` "decouple downlink decoding from RTP receive", is bigger (4 files, `SipHandler.kt` included) and is left out.
