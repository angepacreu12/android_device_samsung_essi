## 1. Who sets the denied properties on stock

rild's denied lookups (task:14-17): `persist.sys.omc_etcpath`, `mdc.omc.update_version`, `ro.csc.country_code`,
`persist.sys.matched_code`, `persist.sys.matched_code2`, `mdc.matched_code`, `mdc.matched_code2`,
`mdc.sys.sec_feature`, `mdc.sys.sec_feature2`.

- **Their label on our image.** `persist.sys.*` falls under `persist.sys.  system_prop`
  (`reference/stock/system/plat_property_contexts:102`; ours `reference/system/system/selinux/plat_property_contexts:103`). `mdc.*` and `ro.csc.*` match no prefix, so
  they are `default_prop`. That is the split the task reports (rild: 50 x `system_prop`, 72 x `default_prop`).
- **Their label on stock.** Not in the reference. Stock's `plat_property_contexts` is plain AOSP for these names
  (`docs/KNOWN_GAPS.md` section 1). Samsung's own lines are in `/system_ext/etc/selinux/system_ext_property_contexts`,
  which we do not have. The stock vendor policy gives two Samsung public types that **every** domain may read:
  `csc_prop` (CIL 11127) and `domain_read_prop` (CIL 11126). Both are in `system_public_property_type` (ppv:69).
  Only `csc_prop` is set by CSC code: `radio` (CIL 8901), `system_server` (CIL 9703), `zygote` (CIL 10202) and
  `scs` (CIL 15912).
- **The setters on stock are all Samsung system-side.**
  - `/system/bin/scs`, run by `S-sys/etc/init/scs.rc:3-8` at `post-fs` (:10-12), at
    `ro.persistent_properties.ready` (:14-16), after decryption (:18-22) and when `mdc.scs.running_state=5` (:24-25).
  - `omc_update`, an init *command* of Samsung's init (`scs.rc:11` and :27-28, on `mdc.omc.img_mount=6`). AOSP init
    has no such builtin, so `scs.rc` would not even parse on our system.
  - The framework: `CSC.apk`, `OMCAgent5.apk`, `framework.jar`, `services.jar`, `telephony-common.jar`
    (`reference/stock/extra/csc/system/binaries_mentioning.txt`).
  - Nothing on the vendor side sets them. The vendor binaries that mention these names are the readers:
    `libsec-ril.so`, `libsemnativecarrierfeature.so`, `libVendorSemTelephonyProps.so`
    (`reference/stock/extra/csc/vendor/binaries_mentioning.txt`). The stock vendor rc files set none of them.
- **Source data.** The sales code is `EUX` (`/mnt/vendor/efs/mps_code.dat`, `docs/CSC_phone_0927.txt:30`). It
  matches `ro.boot.carrierid=EUX` (task:21) and the OMC folder `/optics/configs/carriers/single/EUX/conf`
  (`customer.xml`, `omc.info`, `system/cscfeature.xml`, `system/customer_carrier_feature.json`;
  `docs/CSC_phone_0927.txt:92-99`). On stock, the one property the sales code demonstrably lands in is
  `ro.csc.sales_code` (`S-sys/etc/init/hw/init.rc:2695-2696` binds `/system/carrier/${ro.csc.sales_code}`). rild
  does not look that name up.
- **Values for this phone.** None of the nine can be cited. No stock `getprop` is in the reference, and the
  values are computed by `scs`/`omc_update` from the OMC folder, not copied from a file we have.

## 2. Minimal reproduction

### 2a. CSC/OMC property labels and values: not applied

- **A label alone gives rild nothing.** A denied lookup and a missing property return the same thing to the
  caller. bionic `Find()` logs "Access denied finding property" and returns `nullptr`
  (`libc/system_properties/system_properties.cpp:167-171`). `Get()` then returns an empty value
  (`:259-267`), exactly as for an unset name. Nothing on our image sets these nine names (section 1), so
  labelling them would remove the log lines and leave rild with the same empty strings.
- **The type choice cannot be cited either.** `csc_prop` is the likely type (the CSC setters above), but
  `domain_read_prop` gives the same reads, and the mapping lines are in the missing system_ext file.
- **Ready once values exist.** It uses the PR #18 mechanism (`device/sepolicy_system_ext/`):
  `system_public_prop(csc_prop)` in `public/property.te`, one exact line per name in `private/property_contexts`,
  `get_prop(rild, csc_prop)` and `get_prop(vendor_secril_config_svc, csc_prop)` in `sepolicy_extra/runtime.te`
  (stock: every domain reads it, CIL 11127). The values would be set from a vendor `on boot` action.
- **What is needed.** From the phone running stock AYGE: `getprop | grep -E 'omc|csc|matched_code|sec_feature|mdc\.'`
  gives the values, and `/system_ext/etc/selinux/system_ext_property_contexts` gives the stock labels.

### 2b. `/optics`: already mounted, readable

- Our fstab line (`device/rootdir/etc/fstab.s5e8855`, last line) is the stock one, character for character, as the
  phone prints it (`docs/CSC_phone_0927.txt:7`). The phone shows it mounted read-only (`:4`). Stock's
  `fstab.s5e8855` itself is only listed, not copied (`reference/stock/vendor_ls_Z.txt:408`).
- The mount point exists: `BOARD_ROOT_EXTRA_FOLDERS := prism optics` (`device/BoardConfig.mk`).
- Labels come from the ext4 image's own xattrs. Stock labels them `vendor_file` / `vendor_configs_file`
  (`reference/stock/system/plat_file_contexts:705-706`). Every domain may read `vendor_configs_file`
  (`sepolicy private/domain.te:177-178`). No `/optics` denial was reported. The boot catcher now lists
  `ls -laZ` of the EUX folder to confirm the labels.

### 2c. `/efs`: a directory, the `sec_efs` mount point (added)

- **What stock does.** The vendor script we ship unchanged mounts the `sec_efs` partition on `/efs` at `on fs`
  (`S-ven/etc/init/init.s5e8855.rc:379-380`, identical in `reference/ours/vendor/etc/init/init.s5e8855.rc:379-380`).
  Stock's system `init.rc` then sets `system radio 0771` on it (`S-sys/etc/init/hw/init.rc:952-954`) and creates
  `/efs/sec_efs` and `/efs/rtts` (:957, :960). Stock's system `init.rilcommon.rc` creates `/efs/imei`
  (`S-sys/etc/init/init.rilcommon.rc:54-56`). `fingerprint_common.rc:36-37` creates `/efs/biometrics`.
- **Why the directory is missing.** Our root has no `/efs` (phone, 27/09 19:12). The mount has nowhere to land.
  `BOARD_ROOT_EXTRA_FOLDERS` is the Lineage 22.2 hook that creates extra root directories
  (`system/core/rootdir/create_root_structure.mk:29-31`).
- **Why not a symlink to `/mnt/vendor/efs`.** Three pieces of evidence argue against it:
  - Stock's own `/efs/*` directories are absent from the phone's efs partition. `imei`, `biometrics`, `sec_efs`
    and `rtts` are all missing (`docs/CSC_phone_0927.txt:9-28`), after the phone ran stock. So stock `/efs` is
    not that partition.
  - A symlink would make the `sec_efs` mount above land on `/mnt/vendor/efs`, hiding `nv_data.bin` and the rest.
  - `/efs` must be writable on stock for those `mkdir`s. The system root is read-only. That leaves the `sec_efs`
    mount.
  - The only symlink trace is in recovery (`device/rootdir/vendor_ramdisk_extra/init.recovery.samsung.rc:2-4`,
    "unlink /efs > /mnt/vendor/efs"). That is the recovery ramdisk, which already replaces it with a directory.
- **Label.** `efs_file`, the same on stock (`reference/stock/system/plat_file_contexts:658`) and ours
  (`reference/system/system/selinux/plat_file_contexts:677`, from `sepolicy private/file_contexts:858`). init may
  mount on it: `allow init efs_file:dir mounton` (`device/sepolicy/vendor/platform_and_baseline_domains.te:1015` =
  stock CIL 6291).
- **Risk.** If this device has no `sec_efs` partition, `/efs` stays an empty read-only directory, as harmless as
  today. The boot catcher now prints `ls -l /dev/block/by-name/ | grep efs` and `/proc/mounts` to settle it.
- **cbd's `/efs/factory.prop`.** This PR cannot promise it. It opens only if `sec_efs` holds a `factory.prop`. The
  stock scripts only ever copy it to `/efs/imei/factory.prop` (section 4), and cbd's message says
  "(not support)", which may be its normal answer on this model.

## 3. `ro.vendor.boot.carrierid.param.offset` (added)

- **On stock** it comes from Samsung's **system** `init.rilcommon.rc`:
  `on property:ro.boot.carrierid.param.offset=*` -> `setprop ro.vendor.boot.carrierid.param.offset ...`
  (`S-sys/etc/init/init.rilcommon.rc:71-72`). The same block maps `sales` (:68-69), `im` (:74-75), `me` (:77-78),
  `omcnw` (:80-81) and `sn` (:89-90). That script is not in Lineage, so the vendor names are never set.
- **Added** as `device/rootdir/etc/init/essi.rilcommon.rc`, installed to `/vendor/etc/init/` from
  `device/device.mk`. It carries the six `*.param.offset` lines only. The same stock block also maps
  `debug_level`, `cp_debug_level`, `warranty_bit` and `force_upload` (:83-87, :98-102). No log shows them read,
  and they change modem debug and upload behaviour, so they are left out.
- **SELinux.** The source `ro.boot.*` is `bootloader_prop` (ours `reference/system/system/selinux/plat_property_contexts:1043`; stock :983), readable by every
  domain (`sepolicy private/domain.te:479`). The target `ro.vendor.*` is `vendor_default_prop`
  (`sepolicy private/property_contexts:266`). Stock has no finer label: its `vendor_property_contexts` has no
  `ro.vendor.boot.` line. `vendor_init` may set it (`private/vendor_init.te:305`), and rild reads it
  (`private/domain.te:471`). rild may already read the param partition: `allow rild paramblk_device`
  (`device/sepolicy/vendor/device.te:287`), and `/dev/block/param` is linked by `init.s5e8855.rc:35`.

## 4. Why `ro.multisim.simslotcount` is still empty

- Both inputs of the chain are in place since PR #18: the set is allowed and `/mnt/vendor` is searchable.
- Stock runs two `on fs` actions back to back. First
  `copy /mnt/vendor/efs/factory.prop /efs/imei/factory.prop` (`S-ven/etc/init/init.vendor.onebinary.rc:10-13`, ours
  identical). Then `exec_start sim_config` (`S-ven/etc/init/init.vendor.rilcommon.rc:28-31`). init parses
  `/vendor/etc/init` in sorted order (`system/core/init/parser.cpp:177`), so `onebinary` runs before `rilcommon`.
- `secril_config_svc` may **write** `imei_efs_file` (CIL 18378-18379), the label of `/efs/imei`
  (`S-ven/etc/selinux/vendor_file_contexts:466`). On `efs_file`, which covers `/mnt/vendor/efs`, it may only
  **read** (CIL 18371-18372).
- On our image `/efs` does not exist, so the copy fails. `sim_config` finds no `/efs/imei/factory.prop`, and the
  only trace is "secril_config_service starts" (task:20).
- **Conclusion (inferred).** The input it lacks is `/efs/imei/factory.prop`, which needs `/efs` (change 1). This
  comes from the ordering and the policy above; the `secril_config_svc` binary is not in the reference to confirm
  the path it opens.
- If `/efs/imei` is not on `sec_efs` yet, stock creates it only from system `post-fs-data`
  (`S-sys/etc/init/init.rilcommon.rc:54-56`), after the copy. `vendor_init` has no stock rule on
  `imei_efs_file`, so this PR does not add that `mkdir`.

## 5. CASS

- `cpif: umts_cass is not opened` (6x) is the modem interface driver reporting that nobody opened the `umts_cass`
  channel. Stock opens it from `/vendor/bin/cass`, started at `post-fs-data`, class `core`
  (`S-ven/etc/init/cass.rc:1-9`).
- **Whether registration depends on it: not established.** No file in the reference and no log line ties network
  registration to that channel. The only way to learn it is a boot with `cass` running, which is Ange's decision
  after the separate review. Nothing in this PR touches CASS, VaultKeeper, KG or Knox.
